2. Why block_n = 32?

For decode m = 1, so grid_m = 1. The GPU needs many blocks to fill all 128 CUs. With N = 4096:

block_n = 128
grid_n = 4096 / 128 = 32
grid = 32 blocks
Too few blocks
block_n = 64
grid_n = 4096 / 64 = 64
grid = 64 blocks
Still too few
block_n = 32
grid_n = 4096 / 32 = 128
grid = 128 blocks
Good

get_kernel_config keeps halving block_n until grid is large enough. It stops at 32 because unswizzle_mx_scale_cdna4 needs block_n // 32 >= 1.

4. num_warps Comparison for 16x32 Tile

Tile has 16 * 32 = 512 output elements. Total work is fixed.

num_warps = 4
128 threads
512 / 128 = 4 elements per thread
Warp 1 Warp 2 Warp 3 Warp 4
Each thread has enough work
num_warps = 8
256 threads
512 / 256 = 2 elements per thread
W1W2W3W4 W5W6W7W8
More threads, same work, more overhead

num_warps = 8 does not speed up the kernel because the tile is only 16 rows wide. The vector dot instruction is limited by the small block_m = 16 dimension. More warps just split the same small work into smaller pieces.

5. num_stages Comparison

num_stages controls how many block_k tiles are prefetched into registers.

num_stages = 1
current block_k
Small register footprint
num_stages = 2
current block_k
next block_k
2x register footprint

With block_k = 256, each buffer is large. Holding two buffers per thread uses a lot more registers. This reduces how many blocks can fit on each CU.

6. Occupancy: Why the Tuned Config Is Slower

A CU has a fixed register file and LDS. If each block uses more resources, fewer blocks fit on the CU.

CU with baseline config
Block A
4 warps
1 stage
Block B
4 warps
1 stage
Block C
4 warps
1 stage
Block D
4 warps
1 stage
High occupancy: 4 blocks fit
CU with tuned config
Block A
8 warps
2 stages
Block B
8 warps
2 stages
Low occupancy: only 2 blocks fit

Occupancy = number of blocks/warps that can run on a CU at the same time. Lower occupancy means the CU has fewer warps to switch to when one is waiting for memory. It sits idle, so throughput drops.

8. Summary

Parameter Baseline Tuned Effect
block_m 16 16 Correct small-token tile
block_n 32 32 Chosen to get enough blocks
block_k 256 256 CDNA4 scales need multiple of 256
num_warps 4 8 Too many threads for 16x32 tile
num_stages 1 2 2x register use, reduced occupancy
Throughput ~200 tok/s ~152 tok/s Tuned config is slower

The block_m = 16 and block_n = 32 choices are correct. The slowdown came entirely from num_warps = 8 + num_stages = 2.
